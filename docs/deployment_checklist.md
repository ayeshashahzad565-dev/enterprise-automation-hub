# Production Deployment Checklist

Companion to `docs/docker_deployment.md` (command-level Docker/Compose
operations) and `docs/deployment.md` (architectural rationale). This
document is the practical, one-pass checklist for taking a specific commit
to production, and the standing record of which guarantees are enforced
mechanically rather than by convention.

## 1. Supply-chain guarantees

These are properties of the repository as it stands, not aspirations — each
one is enforced by a CI gate in Section 3.

| Area | Guarantee |
|---|---|
| Dependency declaration | `pyproject.toml` is the single hand-edited source of Python dependencies. `requirements.txt` (production) and `requirements-dev.txt` (dev/test/CI) are exact-version-pinned lockfiles generated from it. |
| Lockfile drift | `scripts/check_lockfile_sync.py` fails CI if any pin stops satisfying the range `pyproject.toml` declares. It deliberately does not diff against a freshly re-resolved `pip-compile` run — that would flag routine upstream patch releases as drift, when pinning a point in time is the intended behavior. |
| Base images | Both Dockerfiles pin their base image by digest (`python:3.11-slim`, `node:22-slim`) rather than by floating tag, so a rebuild next month resolves to the identical base image. |
| Node version | CI, E2E, the security scans, and `frontend/Dockerfile` all pin Node 22, because `@supabase/*` declares `engines.node >= 22`. The committed `package-lock.json` is generated by the npm that ships with Node 22 (10.x), which is stricter than npm 11 about lockfile consistency — regenerate it with that npm, not a newer one. |
| Image provenance | `cd.yml` tags every image with the commit SHA (`type=sha,format=long`) in addition to `latest`, so every deployed image traces back to an exact commit. |

## 2. Pre-deploy checklist

- [ ] **`APP_ENVIRONMENT=production` (or `staging`) is set explicitly.** This is the master switch every other hardening check below depends on (`Environment.requires_production_grade_hardening`) — it defaults to `development` if unset, with no runtime cross-check that this was intentional. Forgetting this one variable silently disables every check in this list: CORS falls back to `localhost:3000`, SMTP becomes optional, `APP_BASE_URL` falls back to `localhost:3000` (breaking every invitation email link), and interactive API docs stay enabled. Verify with `curl <host>/api/v1/health` and confirm `/api/docs` returns `404`, not a Swagger UI.
- [ ] `alembic upgrade head` applied against the target environment's database **before** new application code starts serving traffic (never as an implicit container-startup side effect — see `docs/docker_deployment.md` §6).
- [ ] `.env` (backend) and `frontend/.env.local` populated with the target environment's real Supabase project credentials — never point at a shared staging/production project from a developer machine.
- [ ] `REDIS_URL` set if shared rate limiting / shared analytics cache / the queued email worker are wanted for this environment; every one of those features degrades to its single-process default when unset (no hard Redis requirement).
- [ ] CI green on the target commit: lint (ruff), type-check (mypy), unit/integration tests, both security workflows, both Docker builds.
- [ ] `docker compose -f docker-compose.production.yml config` validates (confirms env-var interpolation resolves; run this after populating `.env`, not before).
- [ ] GHCR image tag to deploy identified — prefer pinning the deploy to the SHA tag, not `latest`, for an auditable rollback point.

## 3. CI/CD gates in place (fail-closed)

| Gate | Blocks on | Workflow |
|---|---|---|
| Lint / type-check / unit tests | Any failure | `ci.yml` |
| Lockfile sync | A pin no longer satisfying `pyproject.toml` | `ci.yml` |
| Python dependency audit (`pip-audit`) | Any known vulnerability (stricter than critical-only) | `security.yml` |
| Frontend dependency audit (`npm audit`) | `critical` severity (high/moderate remain informational — see §4) | `security.yml` |
| Secret scan (`gitleaks`) | Any committed secret | `security.yml` |
| Static analysis (`bandit -ll -ii`) | Medium+ severity, medium+ confidence | `security.yml` |
| Container image scan (Trivy) | `CRITICAL` severity with an available fix, both images | `security.yml` |
| Frontend build | Any `next build` failure | `ci.yml` |

## 4. Known, disclosed, accepted gaps

- **Three high-severity frontend npm advisories are not blocking.** All three (`postcss`, `sharp`, and `next` itself by way of those two) are reachable only through Next.js, and the sole available fix is a major upgrade to `next@16`, which is a breaking change well beyond a dependency patch. Every advisory with a semver-compatible fix has been taken. Zero `critical` advisories remain, which is what `security.yml` gates on. Re-checked on every build; revisit when the Next 16 upgrade is scheduled on its own merits.
- **Lockfiles are version-pinned but not hash-pinned.** `requirements.txt`/`requirements-dev.txt` pin exact versions, so the same versions install every time, but they are not SHA256-hash-verified. **Recommended follow-up**: run `pip-compile --generate-hashes` for both lockfiles from a machine matching the target platform (`python:3.11-slim`, Linux/cp311) and commit the result; `scripts/check_lockfile_sync.py` will not object as long as the versions still satisfy `pyproject.toml`.
- **No automated dependency updates.** The lockfile-sync check catches drift whenever a human bumps `pyproject.toml`, but nothing currently opens that bump automatically. Configuring Dependabot or Renovate is a natural next step.

## 5. Rollback

- `cd.yml` tags every image with the commit SHA (`type=sha,format=long`) in addition to `latest` — redeploying a prior SHA tag is the rollback path; no image is ever overwritten.
- Migrations in this codebase are forward-only in production philosophy (`docs/deployment.md` §11) — a schema rollback is a new forward migration, not `alembic downgrade`, on any environment with real data.

See `docs/database_schema.md` §10.2 for the full index table (including which composite indexes were deliberately *not* added and why), and `tests/unit/test_api_docs_gating.py` / `tests/unit/test_invitation_settings.py` for the regression tests covering the `CORS_ALLOWED_ORIGINS` and `APP_BASE_URL` environment gates referenced in Section 2.
